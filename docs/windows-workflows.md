# Windows 任务模式与独立助手

## 项目 Chief 专用聊天

顶栏“项目 Chief”打开已配置项目的独立聊天，不改变普通聊天或 `/api/send`。
先描述目标、讨论方案，再发送“开始干”“按这个做”“开始执行”或“那你就开始干吧，兄弟”等独立执行消息，宿主调用真实复杂任务调度器；提问、引用这些字词或“不要开始干”不会触发执行。
运行中不重复派工；失败后补充说明，再发送“继续执行”，接回原任务。讨论与执行提交均有幂等编号，刷新页面不会重复创建。

本机配置为 `windows-data/chief-teams.json`，每个团队包含 `id/name/cwd/roles`；五个角色键为 `decision/planner/engineer/evidence/reviewer`，值为绝对目录。工作目录与角色资料目录分开：代码写进项目，宿主把记录写入各角色目录的 `CCBoard/<team-id>/`。
配置可用 `adoptJobIds` 明确登记既有工作流；仅接受相同真实项目目录且未绑定其他团队的任务，保留执行状态，不自动启动，不按标题或普通聊天内容猜测归属。
旧任务误选父目录时，只有显式配置 `adoptNarrowWorkspace: true`、任务未运行且尚无已完成的写入回合，才允许收窄到其子目录；不允许扩大范围。迁移前后路径保存在任务 actions 中。本机旧 CCBoard 任务已从 `D:/项目群组` 收窄到 `D:/项目群组/cc-board`，仍保持 needs_input，未重放。
当前用户的五个 quant 目录已绑定到 CCBoard 项目，保留旧目录名与原 `AGENTS.md`。Chief 承担新增协调职责，decision 保留最终决策参考；tester 独立执行测试，evidence 接收宿主证据归档，不能将二者混为同一职责。

自动保存的文件：

- `ROLE.md`：项目绑定与职责说明。
- `MEMORY.md`：以“记住：…”明确记录的用户偏好，带原话与时间，不自动猜测倾向。
- `HANDOFF.md`：最近任务的阶段结果、状态、错误和线程身份。
- `<job-id>.json`：按任务保存的交接与宿主测试证据；后续任务不覆盖其他任务的记录。

Chief 聊天保存在 `windows-data/chief-chats.json`，执行记录仍在 `workflows.json`。每阶段保存交接，任务停止或结束时同步五个角色目录；记录写入失败会使任务显示失败，不假称保存成功。写入角色目录由宿主执行，模型执行阶段不会因此获得这些目录的写权限。
支持 Chief 使用 `delegate_parallel` 和 2–4 项 `assignments` 派出独立的拆解、研究、编码、文档任务；每批最多两个执行槽位，同一项目只运行一个写入角色。测试等待写入结束，QA 等待测试完成。未接管已有桌面普通聊天。

排队阶段先持久化，收到 Codex `turn/start` 回执后才记录 `executionStartedAt` 并点亮节点，结束后单独熄灭。失败时等待已开工兄弟结束，未启动任务停止；恢复只补未完成分支，保留旧尝试记录。服务重启不会自动重放批次。

入口是“新任务”弹窗右下角的 **开工 →**。悬停展开三个模式，选中只改变模式，
点击开工或 Ctrl/⌘+Enter 才提交。旁边的 ▾ 支持点击，方向键与 Escape 支持键盘。
没有任务文本的一次性提交仍沿用原来的空 Codex 终端入口。已有聊天的回复操作不变。

| 模式 | 实际行为 |
| --- | --- |
| 一次性任务 | 一个真实操作助手完成一轮，展示交付与证据 |
| 复杂任务 | 总负责人按需委派拆解、研究、实现、文档、独立测试与验收；最多 12 阶段、2 次验收返工，未通过则停止并显示原因 |
| 先讨论方案 | 只读讨论和澄清；可继续补充，只有明确点击“按一次性任务执行”或“按复杂任务执行”才操作 |

顶栏“任务流程”显示状态、每阶段真实聊天/回合编号、进展、报告与错误。不同阶段
使用独立的 Codex 聊天，标题带角色及任务内容。总负责人按用户授权使用已核验可用的
`gpt-6.2-astra/high`，禁止静默降级；其他角色沿用用户选择或 Codex 默认。
讨论方案有版本号；过期标签页无法批准新版本。未发送的补充内容也会阻止确认。

## 实现与权限

`workflows.mjs` 是服务端持久状态机，数据在 `windows-data/workflows.json`。
`codex-stage.mjs` 保持 app-server 连接，必须收到匹配聊天和回合的完成通知、有效的
结构化结果，才进入下一阶段。没有真实编号、无证据的完成声明、格式错误、失败或
断线都不会被当成成功。提交和确认带幂等编号；重启后未完成任务显示已中断，不自动重放。

讨论、检查和汇总采用 `read-only` 沙盒，并关闭 Apps、插件、浏览器、电脑操作、
hooks、shell、Code Mode、图像生成和模型内部再委派。临时配置将所有有效配置层中
的 MCP 服务逐个禁用；开始模型回合前核对实际沙盒及 MCP 库存，发现仍可用的服务
就拒绝开始。配置只存在子进程内，不改用户的 Codex 配置，不输出配置或认证信息。

这些阶段由宿主提供独立读取的受限文件快照：深度最多 2、目录项最多 100、文本
最多 64KB，跳过隐藏文件、敏感命名、链接、大型文件等。**检查助手做静态核验，
不会独立运行命令或测试，也不会访问外部服务。** 它必须将无法核验的关键条件
标为未通过。复杂任务另有独立测试执行助手：仅临时测试目录可写，被测项目副本只读，
网络和外部工具禁用。宿主捕获命令、退出码、输出及实际脚本内容，QA 必须引用这些
记录；不能将自述当独立验证。研究角色只额外开放内置网页检索。完整边界见
[层级工作流](hierarchical-workflows.md)。

操作、实现和文档阶段明确使用 workspace-write：项目目录和宿主在 D:\ChatGPT-Temp 下创建的独立临时目录可写，TEMP/TMP/TMPDIR 指向该临时目录；网络默认关闭，其余位置不自动放行。启动时核验实际沙盒，避免继承 CLI 的只读默认值。遇到需要客户端处理的审批、用户输入、认证等请求时，
不自动批准。写入角色的命令审批保持连接并进入 `waiting_approval`，任务流程显示完整命令、目录和原因，用户选择“允许这一次”或“拒绝执行”；悬停节点可点“查看授权”。不提供长期允许，不改变沙盒配置，失效请求不能批准。取消/超时/断线会撤销待处理审批，重启不重放。其他尚不支持的交互仍停止并显示原因；测试/只读角色不通过此入口放宽权限。讨论模式可在任务面板补充回答后重新规划。
操作阶段需要用户处理时，请检查显示的对应聊天，避免另开任务重复已经发生的操作。
工作流停止原因同步显示在聊天卡片，优先于停止清理产生的通用“被打断”标记；之后新开一轮时不再覆盖新状态。
组织图卡片悬停时，停止在当前阶段的执行任务会显示“刷新并继续”。点击保留已完成阶段，从停止处继续调度；写入阶段接回原聊天，先核对已有操作再继续，其他阶段重新运行检查。服务拒绝重复提交、过期阶段和仍在运行的聊天，原有阶段/返工上限继续适用。需要额外审批而客户端尚不支持时，仍显示具体原因，不自动批准。讨论任务仍通过任务流程补充问题。
“请求停止”取消后续调度并请求中断当前回合，不能保证后台子进程已终止，也不撤销
已执行操作。每阶段 30 分钟上限，最多同时运行两个任务。
同一或嵌套目录不能并发写；停止结果不确定时保留目录占用，核对后明确解除，不重放操作。
